A `ProviderError` (any subclass, `ValidationError` included) that carries a registered upstream code and no `category` is now served with the code's category instead of `provider_error`, and its public `source` follows. `UPSTREAM_SCHEMA_ERROR` → `upstream_schema_drift`, `NOT_FOUND`/`not_found`/`NO_DATA` → `upstream_http`, `RATE_LIMITED`/`UPSTREAM_RATE_LIMIT`/`LIMITED_NUMBER_OF_SERVICE_REQUESTS_EXCEEDS_ERROR` → `upstream_rate_limited`, `UPSTREAM_AUTH_ERROR` → `upstream_auth`, `UPSTREAM_ERROR` → `upstream_http`, `BLOCKED` → `anti_bot_blocked`, `UPSTREAM_REJECTED` → `upstream_rejected` (unchanged). Before this, every such throw was served as `source: "apifuse"`, so the health monitor could not attribute a real upstream failure to the upstream and graded it `monitoring_unavailable` instead of `down`. Each registered upstream code now declares its status and category in one row (`SDK_UPSTREAM_ERROR_CODE_REGISTRY`), which also feeds the status map, so served statuses are unchanged. An explicit `category` still wins, an operation-declared rejection status still classifies as `upstream_rejected`, and retryability does not follow the derived category. The SDK's own unknown-operation (`NOT_FOUND`) and unknown-route (`not_found`) responses set an explicit `provider_error` category and stay `source: "apifuse"`. Other codes, including `AUTH_REQUIRED`, `INVALID_REQUEST`, and custom codes, are unchanged. No public API changes.
