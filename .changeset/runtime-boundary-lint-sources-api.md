Expose the runtime boundary lint as a standalone entry point, and correct the `process-env-direct-read` guidance about `env: true`.

- `lintRuntimeBoundarySources(files)` (root entry) runs the `process-env-direct-read`, `node-runtime-module-import`, and `direct-fetch-call` rules over a `{ [providerRootRelativePath]: source }` map without a provider definition, applying the same scope filter as `apifuse check` (tests, recorded fixtures, `.d.ts`, the root `dev.ts`/`start.ts`/`deploy.ts`, and `scripts/`, `tools/`, `bin/` are skipped). It returns `{ diagnostics, information }` — the same `ProviderLintResult` shape the CLI renders, with `@apifuse-allow` acknowledgements as `information`. `RUNTIME_BOUNDARY_RULES`, `RuntimeBoundaryRule`, `ProviderLintInformation`, and `ProviderLintResult` are exported alongside it. The platform contract check can now apply the rules with the monorepo's SDK pin instead of each provider's own pin. Parsing uses the `typescript` package resolved from the installed SDK, which the caller's dependency tree must provide (the SDK lists it as a devDependency only).
- The `process-env-direct-read` remediation and the AUTHORING.md section used to say a value could be declared with "`env: true` for plain settings" and then read with `ctx.env.get`. That was wrong: `ctx.env.get` sees only the declared `secrets[].name` (minus engine-owned names), and `env: true` is the capability declaration that turns the `ctx.env` binding on — a type and runtime gate (`PROVIDER_CAPABILITY_UNDECLARED` without it) that does not widen the readable names. The text now says so, and states that test/E2E toggles are not secrets and are replaced with test doubles or recorded fixtures rather than moved to `ctx.env`. Rule levels are unchanged (still `warn`).
