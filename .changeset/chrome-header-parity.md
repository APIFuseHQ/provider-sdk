Make the stealth transport's HTTP/2 header layer match real Chrome ordering for navigation, fetch/XHR, and JSON POST requests on Windows, macOS, and Linux.

This is breaking: browser profile strings are removed in favor of structured `stealth: { browser, os }` selection at provider, client, session, and request scope. `getStealthProfile` now accepts structured selection and `listStealthProfiles` returns supported browser/OS descriptors; omitted `os` explicitly defaults to `macos`. Version-pinned names still throw with structured replacement guidance. Chrome-discarded fingerprint headers remain transport-owned, while callers may override `Accept`, `Priority`, and `Upgrade-Insecure-Requests`; caller values are outer-whitespace-trimmed and duplicate or array values are joined with `", "` without validation or other rewriting. Fixed per-name slots for caller-supplied HTTP/2 fetch/XHR headers (`stealth.requestClass: "xhr"`) are replaced by a Chromium 149 `HTTPHeaderMap` HashMap bucket-order emulator, so arbitrary header combinations receive Chrome-derived placement; navigation and POST keep their captured fixed orders.

Header order now follows real Chrome rather than the Playwright capture harness. Earlier captures were taken with a DevTools session attached (Playwright's `locale` option), which inserts `Accept-Language` into Blink's header map next to `User-Agent`; a real Chrome sends it where its network layer appends it, after `Accept-Encoding` and before `Cookie` and `Priority`, and that is what the transport emits. The client-wide `stealth.acceptLanguage` default is emitted at that position. On fetch/XHR requests a caller-supplied `Accept-Language` header is placed like any other caller header inside the emulated map and is never emitted twice; on navigation and POST requests it replaces the value at the network-layer position.
